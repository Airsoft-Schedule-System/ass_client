# 게임 운영 화면과 API 검토

검토일: 2026-08-30

## 확인 범위와 근거

- Pencil MCP로 `Design_v2.pen`의 운영 목록, 개요, 게임 생성, 게임 수정, 게임 규칙, 신청자 목록, 신청자 상세 7개 화면을 읽고 수정했다.
- STG `swifztpojovwbpbyvgch`에서 `supabase gen types typescript --schema public`을 실행해 현재 공개 스키마와 RPC 인자를 읽기 전용으로 확인했다. 생성 결과를 프로젝트 타입 파일에 덮어쓰지는 않았다.
- 동작 조건은 백엔드 `0017_remove_prepayment.sql`, `0018_rule_notes.sql`, `0019_occupancy_invariant.sql`, `0021_host_participant_view.sql`과 기존 출석 RPC를 대조했다. 원격 함수 본문까지 직접 조회한 검증은 아니다.
- 기획의 결제·환불 서술은 `ass_knowledge/decisions/2026-08-20-a2-prepayment-removal.md`의 폐기 결정이 우선한다. 규칙 편집은 `decisions/2026-08-20-game-rules-structure.md`를 참고했다.
- 백엔드와 클라이언트 실행 코드는 수정하지 않았다. 기존 백엔드 작업 트리의 변경사항도 그대로 유지했다.

## 화면별 판정과 수정

| 화면           | 확인 결과 및 반영                                                                                                                                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 내가 만든 게임 | 본인 소유 `game_sessions`와 필드 조인으로 구현 가능. 승인 대기 수는 참가 상태 집계. 서버에 없는 `출석 준비` 상태를 `모집중`으로 수정했다.                                                                                            |
| 게임 운영 개요 | 좌석·대기·정원 집계 가능. `confirmed_count`는 `confirmed + attended`이며 미출석 확정자 수와 다르다. 활성 입장권도 별도 조회해야 한다. 취소 마감 안내를 실제 차단으로 오해하지 않도록 수정하고 출석 관리 진입을 목록 기준으로 바꿨다. |
| 게임 생성      | 필드 ID 또는 직접 입력 이름 중 하나, 미래 시작 시각, 정원, 게임비, 최종 규칙이 필요하다. 프리셋/직접 입력 XOR 안내를 제거했다. 취소 관련 날짜는 강제 마감이 아닌 안내 기준으로 표현했다.                                             |
| 게임 수정      | 시작 시각·필드·주최팀·프리셋 출처 ID는 변경 불가. 정원은 증원만, 게임비는 점유 좌석 0일 때만 변경 가능하다. 프리셋 기반 게임의 규칙 변경 불가 안내를 없애고 게임별 규칙 편집으로 수정했다.                                           |
| 게임 규칙      | 탄속 필수, BB탄 무게·바이오탄 여부·탄창 제한 선택, 추가 규칙 텍스트 입력으로 수정했다. 프리셋은 입력값을 복사한 뒤 편집하는 기능이다. 사용자가 JSON을 직접 입력하는 UI는 제거했다.                                                   |
| 참가 신청자    | `list_session_participants`로 구현 가능. 팀명도 RPC 응답을 사용한다. 실제 참가 상태 5종에 맞게 필터를 보완하고 `참가 확정`을 `참석 확정`으로 통일했다.                                                                               |
| 신청자 상세    | 이메일 행 삭제. 승인 대기 예시에서 연락처 행 삭제. 전화번호는 RPC가 값을 반환할 때만 표시한다. 승인/반려 가능 조건을 화면 context에 기록했다.                                                                                        |

각 화면의 `context`에도 조회 API, 상태별 액션 조건, 제외한 기능의 이유를 기록했다. 상태 필터의 예시 숫자는 전체 8명, 승인 대기 2명, 참석 확정 6명이며 목록 카드에는 처음 4명을 표현한다.

## 구현 시 지킬 조건

- 운영 권한은 `game_sessions.created_by_user_id`와 로그인 사용자 ID를 비교한다. 요청 권한의 최종 판단은 RLS/RPC가 한다.
- 승인·반려는 `pendingApproval`이고 세션이 `recruiting` 또는 `closed`일 때만 가능하다. 승인은 정원도 확인하며 서버의 `capacityFilled` 오류 후 현황을 다시 조회한다.
- 게임 수정·취소와 출석 처리는 해당 RPC의 허용 세션 상태를 따른다. `completed`와 `cancelled` 게임은 이 액션들을 제공하지 않는다.
- 참가자 이메일은 호스트 RPC에 없다. `users` 직접 조인으로 우회하지 않는다.
- 전화번호는 `confirmed` 또는 `attended`이고 종료 후 24시간이 지나지 않았을 때만 제공된다. 종료 시각이 없으면 이 연락처 정책에 한해 시작 +6시간을 종료로 계산한다. 번호 자체가 없거나 응답이 null이면 행을 숨긴다.
- RPC의 `entry_pass_status`는 활성 입장권만 조인한다. null을 미발급·만료·사용 완료로 단정하지 않는다. 입장권별 상태와 만료 여부는 `entry_passes`를 별도로 조회한다.
- `cancel_deadline`은 현재 취소 RPC의 차단 조건이 아니다. 안내 기준을 넘었다는 이유로 서버가 취소를 막는다고 표시하지 않는다.
- 변경된 필드만 `update_game_session`에 전송한다. 현재 정원과 같은 값을 보내거나 확정자가 있는데 게임비 필드를 보내도 기존 RPC가 거절할 수 있다.
- 신청자 취소 이력 전체, 과거 취소 사유, 반려 사유를 참가 테이블의 보존 필드처럼 표시하지 않는다. 현재 참가 행에는 해당 필드가 없다.
- 규칙 적용 버튼은 생성/수정 폼의 입력 상태로 돌아간다. 최종 게임 저장 전까지 별도 게임 생성 RPC를 호출하지 않는다.
- 프리셋의 추가 규칙 블록을 텍스트 입력으로 표시하더라도 원래 제목·본문이 조용히 유실되지 않도록 변환해야 한다.
- 로딩·조회 실패·빈 목록·존재하지 않는 게임·권한 없음·제출 중·제출 실패 상태를 구현한다. 사용자 중복 제출을 막고 성공 후 목록·상세·집계를 갱신한다.

## 현재 STG와 다음 스키마의 차이

현재 STG 타입에서 확인한 계약:

- `create_game_session`: `{ p_input: Json }`
- `update_game_session`: `{ p_session_id: string, p_updates: Json }`
- `game_sessions.custom_rules`: `Json`
- 게임 세션에 `muzzle_velocity_fps`, `bb_weight_grams`, `bio_bb_required`, `magazine_limit` 개별 컬럼이 아직 없다.

백엔드 `0023_game_session_rule_text.sql`은 이를 개별 RPC 인자·규칙 컬럼·기타 규칙 문자열로 바꾼다. 현재 STG와 다르므로 적용되었다고 가정하고 화면 코드를 작성하면 안 된다. 적용 이후에는 DB 타입 재생성과 endpoint/변환 코드 변경이 필요하지만, 이번에 정리한 사용자 입력 화면은 유지할 수 있다.

해당 마이그레이션에는 기존 게임과 관련 데이터 삭제도 포함되어 있다. 이번 검토에서는 실행하지 않았다.

## 후속 화면 연결과 검토 한계

- 생성 화면의 다음 목적지인 `32A 주최 정보`, 수정 화면의 `33A 게임 취소`는 기존 연결을 유지했다. 현재 확인한 7개 화면과 별개로 해당 목적지 시안 검토가 필요하다.
- 운영 탭의 입장권·출석 하위 화면도 연결 전에 별도로 확인해야 한다. Pencil의 전체 문서 visitor 조회가 오류를 반환하여 이번에는 노드 ID가 확인된 화면만 수정했다.
- QR 스캔 RPC는 존재하지만 현재 참가 상세에서 QR 표시 UI는 제외된 상태다. 실제 QR 흐름을 활성화하려면 참가자 표시 화면이 먼저 연결되어야 한다. 현재 바로 연결할 수 있는 출석 경로는 확정자 목록과 `mark_attendance`를 사용하는 수동 출석이다.
- 수동 출석 RPC는 참여 ID만 받는다. 사유 입력·출석 취소·노쇼 확정 기능을 지원한다고 가정하지 않는다.
